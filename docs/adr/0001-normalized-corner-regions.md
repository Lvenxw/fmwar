# 0001. 区域一律用归一化的两角点表示

- 状态：已接受
- 日期：2026-02-14（会话日期）

## 背景

需求文档用七个数描述每个区域，例如决斗圈 1 写作：

```
决斗圈1范围：-1354 94 -1693 -1266 172 -1786  x=-1354,y=94,z=-1693,dx=88,dy=78,dz=-93
```

同一行里存在两套互相矛盾的读法：

1. 前三个数是角点 `(x,y,z)`，第四到第六个数是第二个角点；
2. 前三个数是角点，后三个数是 `dx,dy,dz`。

证据表明两种读法都出现过：决斗圈的 `dz` 标注为负而实际数值 172 大于 94，像第二个角点的 y；
dx=88 又与 x 方向的实际跨度 88（-1354 到 -1266）吻合，像增量。
按增量解释提示接收范围 `-1354 39 -2041 -857 320 -1389 dx=497,dy=281,dz=652` 时，
x 跨度 497、z 跨度 652 得到的区域**装不下**场地范围（场地 x 跨度 460、z 跨度 652，
但两者 x 起点相同），按角点解释则恰好各向外扩 37 格。

## 决策

配置里不出现 `dx/dy/dz`。每个区域只写两个角点：

```yaml
regions:
  duel-1:
    min: [-1354, 94, -1693]
    max: [-1266, 172, -1786]
```

加载时统一归一化：逐轴取小值为 min、大值为 max（`Region.of`）。
另外把文档里那个单独出现的 dx 值视为**第二个角点坐标的误写**：
提示接收范围的 x 上界取 `-857`，保证它包含整个场地。

## 后果

- 写反了两个角点不会产生空区域或负体积，只会等价于写对。
- 需求文档的数字不再能直接抄进配置，必须人工拆成两个角点；转换过程记录在
  `config.yml` 的注释里。
- `regions.notify` 必须包含 `regions.arena` 这条不变式由加载期校验保证，
  未来若有人改小 notify，会在控制台与 `/fmwar doctor` 里看到明确报错。
