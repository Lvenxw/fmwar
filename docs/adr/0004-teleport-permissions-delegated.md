# 0004. 传送权限完全交给领地插件，本插件不再自己拦一道

- 状态：已接受
- 日期：2026-02-14（会话日期）

## 背景

需求文档第 27 行要求「保证其他玩家无法传送到领地内或在领地内互相传送」，并写明
「领地传送权限默认为关」，同时提到服务器上用的是 Residence（领地名 `FM`）。

当时的实现按字面理解为「本插件要负责这件事」，于是加了一个传送守卫：
取消一切「从保护区外传送到保护区内」的传送事件。结果是**管理员自己被挡住**——
`/tp <坐标>` 与 `/res tp FM` 都无法进入这些区域。

问题出在**职责重叠**：Residence 本身就有一整套传送权限旗帜（`tp`、`move`、`enderpearl`、
`chorustp` 等），部署时把 `tp` 关掉就已经满足需求。本插件再拦一道，等于在别人的
权限系统之上又叠了一层更严格、且完全不看权限的规则。

## 决策

删除传送守卫（`TeleportGuardListener`），以及为它服务的传送豁免机制
（`GameEngine` 里的 `teleportBypass` 集合与 `isBypassingTeleport`）。
本插件的传送退化为直接调用 `player.teleportAsync(...)`，不做任何权限判断。

「谁能传进哪块地」这一层**只由领地插件决定**：

| 区域 | 领地 | 传送权限 |
| --- | --- | --- |
| 大厅 | `FM` | 常态开放（玩家用 `/res tp FM.start` 进入） |
| 准备房间 | `FM.zb` | 常态关闭，仅入队期间需要放行 |

## 后果

- 管理员与其它插件的传送恢复正常，不再被 FMWar 取消。
- 需求第 27 行的「其他玩家无法传送到领地内」由 Residence 的 `tp` 旗帜承担，
  本插件不再提供该保证。这是**有意的**：重复实现别人的权限系统只会产生冲突，
  而且冲突往往以「管理员也进不去」这种最难排查的形式出现。
- 本插件自己的游戏传送（加入队列 → 准备房间、开局分散、决斗圈、淘汰回大厅）
  同样不再受 FMWar 保护。若将来发现某个领地旗帜确实会拦住插件传送，
  正确的做法是**按该插件的 API 精确放行**（例如调它的权限判断接口），
  而不是恢复一道全局拦截。
