# 0005. 清场扫描未加载区块，而不是开局强加载整片场地

- 状态：已接受
- 日期：2026-10-05（会话日期）

## 背景

需求 118 要求「清空游戏场地范围内所有实体」，清场实现在 `GameEngine.clearArenaEntities()`，
做法是遍历 `World#getEntities()` 并删除落在 `regions.arena` 内的实体。

实际表现是**清场看着执行了，场地里却还留着掉落物**，且这些掉落物会跨局累积。

原因是 `World#getEntities()` 只返回**已加载区块**中的实体。按当前 `config.yml`：

| 项 | 数值 |
| --- | --- |
| X 跨度 | -1354 ~ -894 = 461 格 → 30 个区块列 |
| Z 跨度 | -2041 ~ -1389 = 653 格 → 42 个区块行 |
| 合计 | **约 1260 个区块** |

一局里只有玩家附近的一小部分区块保持加载。掉落物落在远处未加载区块时，
它们并不在`getEntities()` 的结果里，因此永远不会被清掉——未加载区块的实体
本来就存在区块存档（NBT）里，只有把该区块加载上来才看得见。

`regions.arena` 的 y 范围（39~300）对这个数字**没有任何影响**：区块是整列加载的。

## 考虑过的替代方案

### 方案 A：开局强制加载整片场地，结束后卸载

即给全部约 1260 个区块打 `forPluginChunkTicket`，游戏结束后 `unloadChunk`。

**否决。** 代价与收益严重不成比例：

- **常驻内存**：1260 个已加载区块，按每个 1~4 MB 估算约 1.5~5 GB。
- **光照计算**：每个新加载区块都要排队重算光照，上千区块的开局会明显卡顿。
- **每tick 开销**：加 `ENTITY_TICKING` 票后这些区块持续参与实体/方块扫描。
- **票不会自动消失**：即使游戏结束，误加的票会让这 1260 个区块永久常驻，
  两局之间的空闲时间也在占用这些资源；而 `unloadChunk` 只是"请求"，
  区块上有玩家或有其它 ticket 时会直接失败，泄漏难以察觉。

为了清理"几个掉落物"而常驻 1.5~5 GB 内存，是本末倒置。

### 方案 B：直接改写区块 NBT

跳过加载/卸载，直接编辑存档。可行但要处理区块版本、数据压缩、并发写盘，
且无法保证服务端对该区块没有缓存。风险远高于收益，不考虑。

## 决策

新增 `ArenaCleaner`（`cn.mgtown.fmwar.service`），在**结算时**分批处理：

1. **已加载区块**：直接清理（不涉及加载/卸载，不惊动客户端），且**排在队列最前面**。
2. **其余区块**：每 tick 处理 `cleanup.chunks-per-tick` 个（默认 4），
   临时加载 → 删实体 → **立即卸载还原**。

三条硬约束：

- **绝不生成新区块**：只处理 `isChunkGenerated` 为真的区块，且加载时
  `generate=false`。否则会为了清掉落物而在世界上凭空造出新区块。
- **加载前后状态还原**：只卸载本次自己加载的区块。`unloadChunk` 在区块被
  玩家或其它插件占用时会返回 false——宁可留着，也绝不把玩家脚下的区块踢掉。
- **每 tick 限量**：绝不在单个 tick 内把上千个区块处理完。

## 修正一：只扫“对局期间活动过的区块”，而不是场地矩形全量

**初版按场地矩形（约 1260 个区块）全量扫，实测导致客户端卡顿且玩家无法立即回大厅。**
三个叠加的原因：

1. **结算顺序错了（“回不了大厅”的直接原因）**：`finishGame()` 里
   `sendPendingHallToLobby()`（真正把玩家传送回大厅）排在 `clearArenaEntities()`
   **之后**。主线程被清场占住的那一两秒里，回大厅的传送根本还没发出去。
2. **主线程被长时间阻塞**：初版同步遍历全部已加载区块，并一次性派发上千个
   `getChunkAtAsync`。主线程被饿死 → 客户端收不到 tick → 客户端卡顿甚至掉线。
3. **成批加载/卸载惊动客户端**：服务端区块卸载会让客户端地形消失再重绘。

第 3 点暴露了方案的根本浪费：**掉落物只可能产生在“对局期间加载过的区块”里。**
场地矩形有约 1260 个区块，而一局里玩家真正活动过的通常只有几十个——绝大多数区块
玩家从没去过，不可能有掉落物，扫它们纯属自找麻烦。

因此改为：对局中每 20 tick 调一次 `ArenaCleaner#track()`，记录玩家所在区块
（外扩 24 格以覆盖掉落物抛洒范围）；结算时只扫这份名单 + 当前已加载区块。
新一局在 `beginGame()` 里 `resetTracking()`，不继承上一局残留。

## 修正二：`start()` 自身不做任何同步批量工作

`start()` 现在只**排一个从下一 tick 开始的任务**，不碰任何区块。这样调用方后续的
“传送回大厅 / 恢复领地权限”不会被清场阻塞——调用顺序不再是“必须小心调换”，
但仍保留正确顺序（玩家优先）以便阅读时意图明确。

## 后果

- 场地内的残留掉落物会被真正清掉，包括远处未加载区块里的。
- 清场不再是瞬时的：玩家**立刻**回大厅，环境清理在随后若干 tick 内陆续完成，
  收尾时打一条汇总日志（扫描区块数、删除实体数、未能处理的区块数）。
- **`/fmwar stop` 与插件停用只清已加载区块**（`startLoadedOnly()`）。
  停用过程中不能调度异步加载任务，且加载后无人卸载。远处残留留到下次正常结算处理——
  服务器停机时这些区块本来就还在磁盘上。
- 新增配置 `cleanup.enabled` / `cleanup.chunks-per-tick`。关掉 `enabled` 会退回
  旧行为（只清已加载区块），并明确 WARN 提示会残留。
- 若某局没有产生任何追踪记录（例如对局没跑完主循环就被中止），退回到
  “当前已加载区块”这个保守集合，而不是扫全量地形。

## 相关：落点不得进入洞穴

同一轮排查中发现的独立问题（不属于本 ADR 范围，但成因同源——
都是"向下搜索遇到了本不该接受的东西"）：

`SafeLocation.find()` 从 `getHighestBlockYAt()+1` 向下找，遇到液体时是
`continue`——**穿过水面一路落到水底**。若采样点正好落在地下洞穴（有水面），
玩家会被直接丢进洞里。已改为遇液体即 `return null`（作废该列换点），
并新增「无天花板模式下，落点不得低于该列地表 2 格」以挡住干燥竖井口。

注意决斗圈 2（`duel-2`，y 范围 99~101）因 `Settings.resolveExactY` 强制锁定高度，
走 `SafeLocation.exact()`，**不做地形搜索、不受影响**。

## 修正三：奖励箱清理被状态复位短路（内容跨局残留）

**症状**：开局后打开奖励箱，能看到上一局没被取走的物品与新放入的物品混在一起。

**根因不在清场逻辑本身，而在调用顺序**。`finishGame()` / `forceCleanup()` 的收尾顺序是
`resetRuntimeState()` → `clearChests()`，而 `resetRuntimeState()` 里有一句
`chests.clear()`——奖励箱坐标清单在清箱之前就被清空了，`clearChests()` 遍历的是一个空列表，
**一个箱子都没动过**，而且它当时连日志都不打，所以这个问题一直是静默的。

奖励箱方块于是跨局留在场地里；下一局 `spawnChests()` 又只 `setItem` 逐槽覆盖，
而 `chests.loot-groups` 的一行通常 1~2 件、箱子有 27 格，没被覆盖的槽位就把上一局的内容留下了。

**修复**：

1. `resetRuntimeState()` 不再清空 `chests`。它**不是普通运行期状态，而是 `clearChests()`
   的待办清单**——把"待执行任务的输入"混进"清空状态的公共实现"里，必然踩这个坑。
   清空动作归还给 `clearChests()` 自己。
2. `spawnChests()` 写入前 `inventory.clear()`：开局干净不再依赖上一局的清箱是否成功，幂等。
3. `clearChests()` 改用活体方块实体（`getState(false)` + `Container` 接口），并补收尾日志
   `奖励箱：已清空并移除 X/Y 个`——静默是这类 bug 得以长期潜伏的土壤。

**遗留（本次未做）**：`ArenaCleaner` 只删实体，不清**方块容器**（玩家自己在场地里摆的箱子、木桶等）。
需求 118 原文是"清空游戏场地范围内所有实体"，方块容器严格说不属于实体；
若要一并清，需要在区块枚举时顺带扫 `Chunk#getTileEntities()` 并按 `Container` 清空内容。
